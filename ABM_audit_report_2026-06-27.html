1. 보안 관련 주요 허점

HIGHJWT 쿠키 기반 인증에서 CSRF 방어가 약함

영향: access/refresh token을 HttpOnly 쿠키로 사용하고 SameSite=None 구성이 존재합니다. DRF 기본 인증 경로는 CSRF 검사를 강제하지 않는 경우가 많아, 상태 변경 API가 크로스사이트 요청에 노출될 수 있습니다.

근거: backend/config/settings.py:345, backend/config/settings.py:426, backend/apps/users/authentication.py:4

권장: 쿠키 JWT를 유지한다면 상태 변경 API에 CSRF 토큰 검증을 강제하거나, Authorization 헤더 기반으로 단일화하고 SameSite/Origin 검증 정책을 명확히 하세요.

HIGH토큰이 JSON 응답과 localStorage에도 저장됨

영향: HttpOnly 쿠키를 쓰면서 access/refresh를 JSON으로도 내려주고 프론트에서 localStorage에 저장합니다. XSS 발생 시 토큰 탈취 가능성이 커집니다.

근거: backend/apps/users/views.py:647, backend/apps/users/views.py:748, backend/apps/users/views.py:855, frontend/src/shared/api/api.ts:12

권장: 운영에서는 HttpOnly 쿠키 또는 Authorization 헤더 중 하나로 일관화하고, localStorage 토큰 보관을 제거하는 방향이 안전합니다.

HIGHDirect Message 생성 권한 검증 누락

영향: MessageSerializer의 conversation이 writable이고 perform_create에서 요청 사용자가 해당 대화 participant인지 확인하지 않습니다. 대화 ID를 알면 타인의 대화에 메시지를 삽입할 수 있습니다.

근거: backend/apps/direct_messages/serializers.py:8, backend/apps/direct_messages/views.py:56

권장: perform_create에서 conversation.participants에 request.user가 포함되는지 검증하고, serializer에서 conversation 선택 범위를 사용자 소유 대화로 제한하세요.

HIGHDirect Message 수정/삭제 범위 과다

영향: MessageViewSet queryset은 conversation 참여자 기준이라, 같은 대화 참여자가 상대방 메시지까지 수정/삭제할 수 있는 구조일 가능성이 있습니다.

근거: backend/apps/direct_messages/views.py:49

권장: 수정/삭제는 sender 본인 또는 관리자만 가능하도록 object permission을 분리하세요.

HIGH프로필 수정으로 온보딩 학적 검증 우회 가능

영향: 온보딩에서는 학번 형식, 중복, StudentRegistry, 이름 일치, 입학연도 등을 검증하지만 프로필 수정 serializer는 student_id, name, grade, department, admission_year를 거의 그대로 받습니다.

권장: 검증 완료 후 바뀌면 안 되는 필드는 read-only 처리하거나, 변경 시 온보딩과 동일한 검증/재승인 플로우를 적용하세요.

영향: API OTP verify가 AllowAny이고 실패 횟수 제한이 보이지 않습니다. OTP 생성도 random.randint를 사용합니다.

근거: backend/apps/users/views.py:440, backend/apps/users/views.py:800, backend/apps/admin_otp/views.py:25

영향: 접근 endpoint는 권한을 확인하지만, R2 설정은 public bucket 시 서명 URL 불필요(querystring_auth=False)라는 전제입니다. 실제 버킷이 public이면 민감 이미지가 우회 접근될 수 있습니다.

4. 권장 처리 순서

  1. 인증/권한: CSRF, localStorage token, DM conversation 권한, 프로필 학적 검증 우회.
  2. 파일/민감정보: community/network 업로드 검증, R2 private media 정책, PII hash/encryption 재설계.
  3. 남용 방지: OTP attempt lock, 공개 enumeration/page-view throttle, EventLog 길이 검증.
  4. 데이터 정합성: 댓글 parent 소속 검증, self-like/race 처리, like_count clamp.
  5. 운영성: pagination, GET side effect 제거, 관리자/로그 대형 view 분리.
